# Carton Case Management — Cleanup & Re-baseline Research

**Status:** Research / discovery. Nothing in this doc has been executed yet. This is a scratchpad + source of truth for the "new clean main branch" effort.

**Context (why this doc exists):** This repo is a training/workshop vehicle for AI-enablement sessions (Claude Code, GitHub Copilot). Main is supposed to be the stable baseline that workshop branches fork from and stay in sync with. In practice, ~7+ months of iteration, changing AI tooling conventions, and ad-hoc automated-agent branches have left it inconsistent. Goal of the cleanup: a minimal, consistent, **AI-legible** repo where an agent can self-serve setup/debugging for a workshop participant, working from a fresh temp branch that will eventually be merged into `main`.

## 3. Database / Environment Configuration — Confirmed Inconsistencies

This is the most concrete, fixable bug-class found. Prisma resolves a relative SQLite `DATABASE_URL` **relative to `schema.prisma`'s own directory** (`packages/shared/prisma/schema.prisma`), not the repo root and not `cwd`. Every one of these files encodes a different assumption:

| File | `DATABASE_URL` value | Resolves to (relative to `packages/shared/prisma/`) | Correct? |
|---|---|---|---|
| [.env](../.env) | `file:./packages/server/db/dev.db` | `packages/shared/prisma/packages/server/db/dev.db` | ❌ Wrong (but happens to not matter much because... see below) |
| [.env.example](../.env.example) | `file:../../server/db/dev.db` | `packages/server/db/dev.db` | ✅ Correct, and has a comment explaining *why* |
| [packages/server/.env.example](../packages/server/.env.example) | `file:./prisma/dev.db` | `packages/shared/prisma/prisma/dev.db` | ❌ Wrong, and this file isn't even loaded by anything obvious today |
| [.devcontainer/devcontainer.json](../.devcontainer/devcontainer.json) `containerEnv` | `file:./prisma/dev.db` | same as above | ❌ Wrong |
| [docker-compose.dev.yaml](../docker-compose.dev.yaml) | `file:./packages/server/db/dev.db` | matches root `.env` (wrong) | ❌ Wrong |
| [docker-compose.local.yaml](../docker-compose.local.yaml) | `file:./prisma/dev.db` | wrong | ❌ Wrong |
| [docker-compose.test.yaml](../docker-compose.test.yaml) `app` service | `file:./packages/server/db/test.db` | wrong, and points at a `test.db` that nothing seeds | ❌ Wrong |
| [Dockerfile](../Dockerfile) / [Dockerfile.original](../Dockerfile.original) `ENV` | `file:./db/dev.db` | wrong | ❌ Wrong |
| [.github/workflows/ci.yml](../.github/workflows/ci.yml) `e2e-tests` job | `file:./dev.db` | `packages/shared/prisma/dev.db` | ❌ Wrong (harmless in CI only because the runner is thrown away after each job, but still a distinct, undocumented 9th convention) |

**Actual current state on disk:** `find` shows the real db file lives at `packages/server/db/dev.db` (confirmed). So the "correct" value is only the one in `.env.example`. **Every other file in the repo is either wrong, or "wrong but happens to work" for reasons that aren't obvious** — this exact class of confusion is called out as a known trap in my own debugging notes going into this session, and it's confirmed live in this repo, in 6+ places.

**Also note:** the app currently runs fine day-to-day for most people because `.env` at the root is the one npm-scripts (`prisma generate/db push`, run from repo root) actually load via dotenv default behavior, and Prisma silently creates whatever directory path is implied rather than erroring — so a "wrong" value just quietly creates the db in a different (wrong-ish, nested, but git-ignored) folder instead of failing loudly. This is exactly the kind of thing that "works on my machine" and then breaks confusingly for a workshop participant who runs a slightly different command (e.g. `cd packages/server && npx prisma ...`).

**Recommendation direction (not yet executed):** pick ONE canonical `DATABASE_URL` value + ONE canonical way to load env, delete the rest, and add a skill/instruction that tells the agent exactly how Prisma resolves this path so it can self-diagnose "table doesn't exist" / "no such file" errors instantly instead of guessing.

## 4. Runtime / Environment Matrix

The app is designed to run in **4 different ways**, and the user wants to keep supporting most of them (workshop participants have heterogeneous machines: some have Docker, some don't, some are in Codespaces, some in a devcontainer, agents also run cloud workflows). Confirmed run paths:

1. **Bare Node.js** — `npm install && npm run setup && npm run dev` (needs Node 22+/24, no Docker). Playwright needs `npx playwright install --with-deps chromium` (baked into `test:e2e` script itself, which is expensive/slow and network-dependent every run).
2. **VS Code Dev Container** — `.devcontainer/devcontainer.json` → `docker-compose.dev.yaml` → `.devcontainer/Dockerfile`. `postCreateCommand` copies `packages/server/.env.example` → `packages/server/.env` (a file that nothing else in the repo reads/needs, since the real `.env` is at root) then does `npm install && npm run setup`; `postStartCommand` runs `npm run dev`.
3. **Plain `docker compose`** (no devcontainer, e.g. someone without Docker Desktop's VS Code integration, or CI-like local testing) — `docker-compose.local.yaml` (dev loop, self-contained command) or `docker-compose.yaml` (prod-like, built from `Dockerfile.aws`).
4. **GitHub Codespaces** — presumably reuses `.devcontainer/`, not verified/tested here — **open question below**.
5. **Playwright/test runs in Docker** — `docker-compose.test.yaml` spins up an `app` service + a `tests` service, `sleep 5` then runs unit + e2e sequentially. This is a *fifth* path, essentially a hand-rolled CI runner, duplicating what `.github/workflows/ci.yml` presumably also does.

**Open problem:** headed Playwright (`test:e2e:watch` / UI mode) fundamentally can't run inside a devcontainer/Docker without X11 forwarding or similar — confirmed relevant because some workshops specifically want a headed browser demo. Today there's no documented guidance on when to drop out of the devcontainer for that.

**Port map (for reference, gathered from compose/devcontainer files):** 5173 (client/vite), 3001 (server), 6006 (storybook), 9323 (playwright html report).

## 11. `/help` Debugging Skill (proposed, per your request)

You asked for a `/help` slash-command skill so a workshop participant can vaguely describe a problem and have the agent diagnose it, rather than you personally debugging everyone's machine live.

**Design sketch** (matches the VS Code Agent Skills spec researched in §7 — `name` must equal the directory name, lowercase+hyphens):

- Location: `.claude/skills/help/SKILL.md` (auto-discovered by both Claude Code and Copilot per §7's findings; appears as `/help` in both).
- `description` should be written so the agent **proactively** reaches for it any time something looks like a setup/runtime failure, not only when the user literally types `/help` — e.g. "Diagnose and fix local dev environment problems for this repo: server/client won't start, port conflicts, database errors, Docker/devcontainer issues, failing tests. Use whenever the user reports something not working, pastes an error message, or asks for help getting the app running."
- Body should give the agent a **decision tree**, not just prose, e.g.:
  1. Ask (or infer from the error text) which runtime they're in: bare Node, VS Code devcontainer, plain `docker compose`, Codespaces.
  2. Check the fundamentals in order: Node version (`node -v` vs `.nvmrc`), is `npm install` complete (`node_modules` present in root + all 3 packages), does the db file exist at the canonical path, is it seeded, are the required ports free (delegates to the port-conflict skill in §12), is `DATABASE_URL` set/correct for their runtime.
  3. Map common error signatures to fixes (e.g. `EADDRINUSE` → port skill; `P1003`/"does not exist" from Prisma → db path/seed issue; `ECONNREFUSED` on `localhost:3001` from the client → server not running or wrong port; blank Playwright report → browsers not installed).
  4. Always show the participant the exact command(s) to run, don't just silently fix things behind their back when they're trying to learn the tool.
- This depends on §3's `DATABASE_URL` cleanup and §12/§13 below being resolved first — the skill's diagnostic steps are much shorter and more reliable if there's only one correct path/port/db convention to check against instead of nine.

## 12. Cross-Platform Port Conflict Handling (proposed, per your request)

**Problem confirmed:** ports 5173 (client), 3001 (server), 6006 (storybook), 9323 (playwright report) are hardcoded across `playwright.config.ts`, all compose files, and `devcontainer.json`. When a stale process (a previous `npm run dev`, a previous devcontainer, a previous Docker Compose run) is still holding one of these, the next start either fails outright or Vite/Node silently jumps to the next free port — which then doesn't match anything in the workshop instructions, exactly as you described.

**Two distinct failure modes to handle, researched:**
1. **A native process on the host (or inside the current container) is holding the port.** Standard fix is OS-specific: `lsof -ti:5173 | xargs kill -9` (macOS/Linux, including inside a Linux devcontainer/WSL2), vs. `netstat -ano | findstr :5173` + `taskkill /PID <pid> /F` (native Windows, i.e. someone running bare Node directly on Windows rather than through WSL2/devcontainer).
2. **A previous Docker container/compose stack still has the port bound.** Killing a host process won't fix this — you have to `docker ps --filter "publish=5173"` and `docker stop`/`docker compose down` the offending container instead. An agent needs to check for this case separately from case 1.

**Tooling options researched:**
- [`kill-port`](https://www.npmjs.com/package/kill-port) (npm, cross-platform, ~1.9M weekly downloads) — simple `npx kill-port 5173` one-liner works on Windows/macOS/Linux. Caveat: last published ~4 years ago, minimal maintenance activity — fine for a small workshop utility, but worth knowing it's not actively maintained.
- [`get-port`](https://www.npmjs.com/package/get-port) (npm, sindresorhus, actively maintained) — solves the *opposite* problem (finding a free port) rather than freeing a specific one; more useful if we instead decide "pick whatever port is free and tell the user" is an acceptable strategy for some services (e.g. Storybook) but not others where the port number is baked into workshop instructions (client/server).
- A small custom script in the repo (e.g. `scripts/free-ports.mjs`) using Node's `os.platform()` to branch between the lsof/kill and netstat/taskkill commands, plus a `docker ps --filter publish=` check — more code to own, but no dependency-maintenance risk and can be tailored to also print what it's about to kill for transparency (important in a teaching context — silently killing a process without explanation is bad pedagogy).

**Recommendation direction:** given this is a teaching tool where transparency matters (you don't want the agent silently killing things participants don't understand), lean toward a small owned script/skill that (a) reports what's currently bound to each of the 4 known ports and how (native process vs Docker container), (b) asks for confirmation or just clearly explains before freeing it, and (c) is invoked automatically by the `/help` skill and optionally as a pre-flight step before `npm run dev`. Whether to also pull in `kill-port` under the hood to shortcut the cross-platform command differences, vs. writing the OS branching directly, is a small open question — leaning toward *not* adding a 4-years-stale dependency for something this small.

### 16.3 Per-test E2E database isolation (revised after researching standard practice)

Your round-1 answer asked for the database to reset **between every individual test**. Before executing that, I looked into what's actually standard practice industry-wide, since it changes the recommendation:

**Researched findings:**
- [Prisma's own integration-testing guide](https://www.prisma.io/docs/guides/testing/integration-testing) documents the standard flow as: spin up a disposable database → migrate schema → **seed once** → run the **whole suite** → tear down. The reset/seed happens in `beforeAll`/global setup, not before every individual test.
- [Playwright's official docs on parallelism](https://playwright.dev/docs/test-parallel) address this *exact* scenario ("Isolate test data between parallel workers") and their recommended pattern is **not** "reset a shared database between tests." Instead: give each parallel **worker** its own isolated slice of data (their example creates a worker-unique user via `testInfo.workerIndex` in a worker-scoped fixture) so workers never collide — the database itself doesn't get wiped mid-run at all.
- The other half of standard practice: well-written e2e tests are **self-isolating via unique data** (timestamps/UUIDs/worker-index baked into whatever a test creates) rather than depending on a pristine database before every test. This is what actually lets teams run e2e suites in parallel at all — resetting a shared file between every test doesn't fix concurrency, it makes it *worse*, since two workers mid-test could have the rug pulled out from under them by a third worker's reset.

**Net conclusion: full reset-before-every-test isn't the standard pattern, and doesn't actually solve the concurrency problem you were worried about — it's a distinct concern from data isolation.** Revised recommendation, aligned with both sources above:

1. Extract the wipe-and-reseed logic already in [packages/server/db/seed.ts](../packages/server/db/seed.ts) into a small reusable function (e.g. `resetAndSeed()`) — reused by `db:seed` and the e2e setup below, no duplicated logic.
2. **Once per e2e run** (Playwright `globalSetup`, not per test): push the schema + call `resetAndSeed()` against the dedicated test db file (§13's `packages/server/db/test.db`) — this replaces the "before every test" reset and matches Prisma's documented pattern.
3. **Concurrency handled the way Playwright itself recommends**, not via constant resets: either (a) keep `workers: 1` for the e2e project so tests never run concurrently against the one SQLite file (simplest, matches this repo's current small test count, some wall-clock cost), or (b) if/when the suite grows enough that parallelism matters, adopt Playwright's worker-isolation fixture pattern — but that's a bigger lift than this cleanup needs right now.
4. **Tests that create data should still use unique values** (e.g. `create-case.spec.ts` creating a case titled with a timestamp/random suffix instead of a fixed literal) so re-running the suite repeatedly doesn't leave ambiguous duplicate rows even within a single run — cheap to do, and it's the actual mechanism that prevents "one test's leftover data breaks another test," which full resets don't fully guarantee anyway (e.g., two tests both asserting "exactly 3 cases in the list" would still collide with each other if run in the same reset cycle without unique data).

**Revised question for you:** given this is the standard/recommended pattern (once-per-run reset + `workers: 1` for now, rather than per-test reset), are you good with this simpler approach instead of your original per-test-reset ask? It solves the "muddies up local dev data" and "one test's data affects another run" problems you raised, without the concurrency risk a per-test reset would have actually introduced.

### 16.4 Running e2e alongside an already-running dev server (new requirement)
